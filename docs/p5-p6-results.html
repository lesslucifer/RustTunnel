RustTunnel — P5–P6 Results and Final E2E Report

The tunnel now survives its peer going away, its network going away, and its own process being killed by the operating system. Every WBS task that one Mac can run has been run. The report closes with all 23, and with the four claims this machine still cannot make.

Draft v1 · 2026-08-08 · RustTunnel

Verdict

Everything one machine can prove is now proven, and the gate is still open. 2.2 — cross-NAT direct has not been run, so the claim that motivated v2 over v1's relay remains unverified. P5 and P6 were built on top of it anyway, as a stated decision. Nothing in them depends on hole punching: resilience is a retry loop and a QUIC idle timer, and shipping is a build matrix. If 2.2 eventually reports relayed at both ends, none of this code becomes wrong — only the latency argument does.

Proven

A peer that disappears is retried on a 1·2·4·8·16·30 s ladder and picked back up with no restart. A refusal is terminal and exits non-zero. A real Wi-Fi interface loss is survived unattended. Both processes held an hour of periodic 25 MiB transfers with flat memory. A launchd-started serve is a real serve, and KeepAlive brings it back from kill -9. The installer works on a machine with no toolchain.

Not proven

A 24-hour soak — the run was one hour. A real reboot, a real suspend, an asymmetric network loss, a Linux or Windows install, a release page. All of them want either a second machine, a git remote, or a human at the keyboard.

Found by running it

The exit-status bug the WBS predicted, a session table that would have gone stale across a reconnect, a harness bug that killed a wrapper instead of a process and broke the next two checks, and a documentation bug in the pairing walkthrough — caught by 6.4 doing exactly what 6.4 is for.

What was built

P5 is one loop in one file. P6 is five files that contain no Rust at all.

stateDiagram-v2
  [*] --> Binding
  Binding --> Dialing: listeners bound once, kept across every reconnect
  Dialing --> Forwarding: connected
  Dialing --> Waiting: dial failed (iroh gives up after 30 s)
  Forwarding --> Waiting: connection lost — peer gone, network gone
  Forwarding --> Refused: ApplicationClosed
  Refused --> [*]: exit 1, no retry
  Waiting --> Dialing: sleep 1s → 2s → 4s → 8s → 16s → 30s ceiling
  note right of Forwarding
    per-connection: TCP accept loops,
    UDP pumps, session table, reaper.
    All aborted when the link dies, so
    the next link starts with an empty table.
  end note
Hình 1 — The connecting side's lifecycle. The listeners sit outside the loop; everything that carries bytes sits inside it.
FileWhat it adds
src/connect.rsThe loop above. +60 lines: the dial becomes a loop, the listeners become Arcs so a reconnect can reuse them, and the per-connection tasks move into one function that returns their abort handles.

A deviation from the plan of record. The implementation plan says cargo dist init — one command producing the matrix, the installers, an MSI and a Homebrew tap. What is filed instead is a hand-written workflow plus two installer scripts, about a hundred lines total. The reason is verification, not taste: cargo dist is not installed here, its output could not be run either (the release page needs a remote), and the pieces that can be checked on this machine — the archive name, the checksum file, the installer against a file:// base — are the ones written by hand. Switch to cargo dist when the MSI and the Homebrew tap are actually wanted; the artifact names are the same either way.

Thirty seconds is the honest recovery number, and it is not the retry loop's fault. Every recovery in P5 and P6 that started with a peer dying — rather than a peer coming back — waited about half a minute before the first retry, because nothing tells a QUIC endpoint its peer is gone; the idle timer has to expire. The ladder's first rung is 1 s and irrelevant next to that. Shortening it means shortening the idle timeout, which trades a faster recovery for more traffic on an idle link. Worth doing only if someone complains.

Findings

FindingDisposition
1 The exit-status bug the WBS predicted. connect exited 0 when the allowlist refused it. Harmless until 5.1 added a retry loop, at which point a permanent refusal would have been retried forever. Fixed. ApplicationClosed is terminal and exits non-zero; everything else retries. Both halves are asserted in 5.1's transcript and in an in-process test.
2 A reconnect would have reused stale UDP session ids. The far side's session table dies with the connection, so ids minted before the drop would have addressed a table that no longer exists. Fixed by construction: the table and every pump live inside the per-connection scope and are aborted when the link dies. The next link starts numbering at 1 against an empty far table.
3 A new instance of the "kill by pid" trap, and a harness bug. 6.4 backgrounded a shell function, so $! was the subshell, not rtun. Cleanup killed the wrapper and left rtun holding 127.0.0.1:2222, which then failed the next two checks with symptoms that looked like product bugs. Fixed in the harness, and worth adding to the fake-green traps: "kill by pid, never by pattern" is not enough — the pid has to be the process, not its wrapper. Both affected checks were re-run clean.
4 6.4 found a documentation bug on its first pass. The walkthrough's only example was --tcp 22, and Remote Login is off by default on macOS with no way to turn it on without admin. A reader on a stock Mac stalls at step 3. Fixed: the walkthrough now carries a callout naming an unprivileged alternative and threading it through step 5. The check was re-run against the fixed doc.
5 A service does not inherit your identity. A systemd unit with DynamicUser, or a Windows task as SYSTEM, gets its own state directory and therefore its own endpoint id — so the peer's --allow will not match the id you read from your own shell. Documented rather than coded around, in step 6: start the service once, read its id from its own log, then allowlist that. The launchd template names RTUN_STATE_DIR outright for the same reason.

Every P3 and P4 check was re-run against the P5 binary. The reconnect loop touched the connecting side's data plane — the listeners became shared, and the UDP session table moved inside the per-connection scope — so the earlier transcripts no longer described the shipped code. All fifteen filed transcripts under evidence/local/ now name the same sha256, and cargo test's eight in-process checks pass alongside them. Two of those re-runs failed first, on the leaked-listener trap above, and were re-run clean after the harness was fixed.
