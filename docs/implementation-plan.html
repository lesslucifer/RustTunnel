RustTunnel — Implementation Plan

A single-binary Rust CLI that forwards TCP and UDP ports between two machines you own, over a direct hole-punched QUIC connection.

Draft v2 · 2026-08-08 · RustTunnel

Scope

RustTunnel connects two machines you control, each of which may be behind NAT, and forwards a configured list of TCP and UDP ports between them. The connection is direct whenever the network permits it — traffic does not pass through any third party.

What it is

Run rtun on both ends. One side offers local ports, the other side reaches them on its own loopback. Dial by public key, not by address.

What it is not

No virtual IPs, no TUN device, no root, no mesh, no public ingress. An unmodified peer running plain ssh or a browser cannot reach you — only machines running rtun can.

The trade being made: both ends must run our software, because hole punching is something two programs do to each other. In exchange, the common case has no relay in the data path — no rented bandwidth, no third party holding your bytes, and latency is the direct path rather than a detour.

What changed from v1

v1 of this plan was a relay: a VPS with a public IP accepted all inbound traffic and forwarded it down a tunnel. Every byte crossed the VPS twice, the VPS terminated TLS and therefore saw plaintext, and bandwidth was the dominant cost.

v2 removes the relay from the data path. The cost of that removal is stated plainly in Scope: the far peer must run rtun. That single requirement is what makes everything else possible.

v1 — relayv2 — direct
Data pathAlways through the VPSDirect, ~90% of the time; relayed fallback otherwise
Peer requirementNothing — plain ssh worksMust run rtun
Public ingressYes — ssh -p 2222 vps.example.comNo. This is the thing that is genuinely lost.
Who sees plaintextThe VPS, unavoidablyNobody. End-to-end between the two endpoint keys.
Server costMetered egress on every byteKilobytes per handshake, or a free public service
Secrets out of bandShared token + certificate fingerprintTwo public keys. Nothing secret travels.

How a direct connection is possible

A machine behind NAT has no address anyone can dial — that much was true in v1 and is still true. What v1 missed is that the problem is only unsolvable in one direction. If both machines dial out at the same moment, each one's outbound packet creates the NAT mapping that lets the other one's packet in. Neither side ever accepts an unsolicited inbound packet; both sides think they initiated.

sequenceDiagram
  participant A as Machine A behind NAT A
  participant B as Broker with public IP
  participant C as Machine C behind NAT C
  A->>B: I am here, my observed address is 1.2.3.4:41000
  C->>B: I am here, my observed address is 5.6.7.8:52000
  B-->>A: C is at 5.6.7.8:52000
  B-->>C: A is at 1.2.3.4:41000
  Note over A,C: both now fire outbound, simultaneously
  A->>C: UDP to 5.6.7.8:52000 (opens NAT A's mapping)
  C->>A: UDP to 1.2.3.4:41000 (opens NAT C's mapping)
  Note over A,C: each mapping now admits the other's packets
  A->>C: QUIC handshake, direct
  Note over B: broker drops out of the path entirely
Hình 1 — Simultaneous open. The broker never carries payload; it only tells each side where the other appeared to come from.

The broker is unavoidable and small. Neither machine can learn its own public address, or the other's, without asking something that already has one. But that exchange is a few kilobytes once per connection, not a bandwidth line item.

When it does not work

Hole punching depends on the NAT reusing the same external port for packets to different destinations. Most NATs do. Symmetric NAT does not — it picks a fresh external port per destination, so the address the broker observed is not the address the far side must send to. Two symmetric NATs facing each other cannot be punched at all.

SituationOutcome
Both on the same LANDirect, discovered locally. Never leaves the switch.
Either side has a real public IP or working IPv6Direct, trivially.
Ordinary home / office NAT on both sidesDirect, via the punch above.
Router speaks UPnP-IGD, NAT-PMP or PCPDirect — just ask the router for a mapping.
Symmetric NAT on one sideUsually still direct. The non-symmetric side is punchable.
Symmetric NAT on both sidesRelayed. Carrier CGNAT and some corporate networks. No amount of cleverness fixes this.
A relay fallback is not optional. Roughly one connection in ten cannot be punched. Without a fallback those connections simply fail, with no diagnostic the user can act on. The fallback exists so that "it works" does not carry an asterisk — and because the traffic is end-to-end encrypted, falling back costs privacy nothing.

Note the inversion from v1: the listening sockets now live on the connecting machine's loopback, not on a public host. ssh -p 2222 127.0.0.1 on the laptop reaches sshd on the home box.

Transport decision: iroh

QUIC is still the right transport, for the reasons v1 gave — one stream per tunnelled connection so a loss on one does not stall the others, native unreliable datagrams for UDP, and TLS 1.3 built in. What changes is that we no longer drive quinn directly.

iroh is quinn plus the entire NAT-traversal problem, as one dependency. It reached 1.0 and hands the application an ordinary QUIC Connection — the data-plane code below is written against that, unaware of how the connection was obtained.

ProblemHand-rollediroh
Learning your own public addressSTUN client, plus a STUN server to runBuilt in
Exchanging candidatesA signalling protocol and a server to host itBuilt in, public infrastructure available
The punch itselfSimultaneous open, retries, path validation, race handlingBuilt in
Router port mappingUPnP-IGD, NAT-PMP and PCP clientsBuilt in
Same-LAN shortcutmDNS discoveryBuilt in
Relay fallbackWrite and host a relayBuilt in, self-hostable
Peer identityCertificate generation and pinningThe public key is the TLS identity

Every row is a week we are not spending. The alternatives were considered and rejected: libp2p brings a peer-to-peer worldview far larger than a port forwarder needs, and webrtc-rs drags in SDP and the full ICE stack to reach the same place.

The shape of it

// the machine offering ports
let ep = Endpoint::builder(presets::N0)
    .alpns(vec![b"rtun/0".to_vec()])
    .secret_key(persisted_key)
    .bind().await?;
let conn = ep.accept().await?.await?;

// the machine reaching them
let ep = Endpoint::bind(presets::N0).await?;
let conn = ep.connect(endpoint_id, b"rtun/0").await?;

After those four lines the connection is a QUIC connection. open_bi, accept_bi, send_datagram and read_datagram behave exactly as they would on raw quinn.

Persist the secret key on first run. The endpoint's identity is its keypair. Generate one on first run and write it to the state directory with mode 600; if it is regenerated each start, the endpoint ID changes, every allowlist entry pointing at it goes stale, and the far side correctly refuses to connect.

Connection establishment

Setup goes through the relay so the two sides can talk before they can talk directly; the punch happens underneath and the path upgrades in place. Nothing above the QUIC layer observes the switch.

sequenceDiagram
  participant C as rtun connect
  participant R as Relay plus discovery
  participant S as rtun serve
  Note over S: on start, registers home relay and observed addresses
  C->>R: resolve endpoint id to relay url and candidate addresses
  C->>R: QUIC handshake, relayed
  R->>S: forwarded
  S-->>C: connection established, currently relayed
  Note over C,S: allowlist check on the serve side, drop if the peer key is unknown
  par hole punch, concurrent with traffic
    C->>S: probe candidate addresses directly
  and
    S->>C: probe candidate addresses directly
  end
  Note over C,S: direct path validated, QUIC migrates to it
  Note over R: relay is no longer in the data path
Hình 3 — Traffic starts flowing before the punch completes, so the upgrade is invisible except in the logs. If the punch never succeeds the connection keeps working, relayed.
Log the connection type, and make it queryable. Direct versus relayed is the single most useful diagnostic this tool has, and the only way a user learns their network is the hard kind. Print it on establishment and on every upgrade. A rtun status subcommand that reports the current path is worth the twenty lines.

Data plane — TCP

One QUIC bidirectional stream per accepted TCP connection, opened by the connecting side — the inverse of v1, because that is now where traffic arrives first. The stream carries a two-byte header naming the target port on the serving side, then raw bytes in both directions until either end closes.

sequenceDiagram
  participant U as Local process on the laptop
  participant C as rtun connect
  participant S as rtun serve
  participant L as sshd port 22
  U->>C: TCP connect to 127.0.0.1:2222
  Note over C: mapping 2222 to 22 comes from --tcp on this side
  C->>S: open QUIC bidi stream
  C->>S: header u16 target_port = 22
  Note over S: reject unless 22 is in the serve allowlist
  S->>L: TCP connect 127.0.0.1:22
  L-->>S: established
  loop until either end closes
    U->>C: bytes
    C->>S: stream write
    S->>L: bytes
    L->>S: bytes
    S->>C: stream write
    C->>U: bytes
  end
  Note over C,S: stream FIN maps to TCP FIN in both directions
Hình 4 — TCP forwarding. Each connection is an isolated QUIC stream, so one slow transfer cannot stall another.

Both directions are a plain tokio::io::copy pair — the stream halves and the TCP socket halves are all AsyncRead/AsyncWrite, so no custom pump loop is needed. This is unchanged from v1 and is the one part of the design the pivot did not touch.

Data plane — UDP

UDP has no connections, so the connecting side synthesises sessions: the tuple (local source address, target port) is mapped to a u32 session id. Every datagram carries the id and the target port as a six-byte prefix, which is how replies find their way back to the right local process.

sequenceDiagram
  participant U as Local process on the laptop
  participant C as rtun connect
  participant S as rtun serve
  participant L as wireguard port 51820
  U->>C: UDP packet to 127.0.0.1:51820
  Note over C: look up or create session id
keyed by source addr and target port
  C->>S: QUIC datagram, u32 session_id, u16 port, payload
  Note over S: look up or create a UDP socket
dedicated to this session id
  S->>L: sendto 127.0.0.1:51820
  L->>S: reply
  S->>C: QUIC datagram, same session_id, payload
  C->>U: sendto the original source addr
  Note over C,S: session and socket dropped after 60s idle
Hình 5 — UDP forwarding. The session id is the only state; both sides reap it on an idle timer.

The port travels in every datagram rather than being negotiated once, because datagrams are unreliable and unordered — a setup message could be the one that gets lost. Six bytes per datagram buys the absence of that failure mode.

Wire protocol

Two message shapes, and no handshake at all. The identity layer already authenticated both ends before the first byte of application data, and the port mapping lives entirely on the connecting side, so there is nothing left to negotiate.

ChannelOpened byPayload
Data stream Connecting side, one per inbound TCP connection u16 target port, then opaque bytes.
Datagram Either side u32 session id, u16 target port, then opaque bytes.

v1 needed a length-prefixed JSON handshake to carry a token and a port list. Both are gone — serde and serde_json leave the dependency list with them.

Identity and authorization

Each endpoint has an ed25519 keypair, and its public key is both its address and its TLS identity. Dialing by endpoint ID is therefore mutually authenticated by construction: a machine-in-the-middle would need the private key it is impersonating.

The connecting side knows who it reached

It dialed a specific public key. The QUIC handshake cannot complete against anything else. No fingerprint flag, no pinning logic, no way to forget to check.

The serving side decides who may in

An allowlist of endpoint IDs, given as repeatable --allow flags. Any other peer is dropped immediately after the handshake reveals its key.

Nothing secret travels out of band any more. v1 required a shared token to reach the client through a trusted channel — a real operational hazard, since a leaked token was full access. v2 exchanges two public keys. Publishing them costs nothing: knowing an endpoint ID lets you attempt a connection, and the allowlist rejects it. The private keys never leave the machines that generated them.

Port-level authorization lives on the serving side too. rtun serve --tcp 22 --udp 51820 is an allowlist, not a mapping — it states which local ports may be reached at all. A stream naming any other port is refused. Without this, one allowlisted peer could reach every port on the loopback interface, which is a larger grant than the flags suggest.

CLI surface

# on the machine with the services — offers ports, accepts connections
rtun serve --tcp 22 --udp 51820 --allow k51qzi5uqu5dl…
# prints: endpoint id k51qzi5uqu5dh9…

# on the machine that wants to reach them — binds local listeners
rtun connect k51qzi5uqu5dh9… --tcp 2222:22 --udp 51820:51820
# prints: connected, path=direct
# then:   ssh -p 2222 127.0.0.1

# either side, to print its own endpoint id without connecting
rtun id

Mappings are local:remote on the connecting side and bare port numbers on the serving side. The asymmetry is deliberate: only the connecting side needs to choose local port numbers, and only the serving side needs to decide what is exposed.

The endpoint IDs are chicken-and-egg — each side needs the other's before either can start. rtun id exists so both can be read off before any connection is attempted.

Code layout

FileHolds
src/main.rsclap definitions, key persistence, dispatch to serve, connect or id
src/proto.rsstream and datagram framing, endpoint id parsing

The two role files are near-mirrors of each other, but not identical enough to unify — the session tables are keyed differently and only one side holds an allowlist. Two honest files beat one file with a role flag threaded through it.

Build order

MilestoneDone when
M1 Two endpoints meet Both sides print a stable endpoint id across restarts; connect reaches serve by id; a non-allowlisted peer is refused. No forwarding yet.
M2 Confirmed direct The log reports path=direct between two machines on different NATs, not merely on the same LAN. Do this before writing any forwarding code — it is the milestone that validates the whole premise.
M3 TCP forwarding ssh -p 2222 127.0.0.1 reaches the far machine. Multiple simultaneous connections stay independent. Non-allowlisted ports refused.
M4 UDP forwarding A DNS query and a WireGuard handshake both complete through the tunnel. Idle sessions are reaped.
M5 Survives reality Reconnects with exponential backoff after the link drops; survives a laptop sleep, a Wi-Fi to cellular switch, and a NAT rebind without manual intervention.
M6 Shipped Binaries for Linux, macOS and Windows; installed and running unattended under each platform's service manager; surviving a reboot on all three.
M2 is the risk milestone and it comes early on purpose. Everything after it is ordinary byte plumbing that v1 already specified. If your two networks turn out to be symmetric-NAT on both sides, you learn it in an afternoon rather than after building the entire data plane on an assumption. Test across two genuinely different networks — a laptop tethered to a phone is the cheapest second network there is.

The one check

tests/tunnel.rs starts both roles in-process on loopback with ephemeral keys, then asserts round-trips against throwaway echo services:

  • a TCP echo, verifying byte-exact round-trip over the tunnel;
  • two concurrent TCP connections, verifying their payloads do not cross;
  • a UDP echo, verifying datagram round-trip and that the reply reaches the correct local source;
  • a connection from a non-allowlisted key, verifying it is refused;
  • a stream naming a non-allowlisted port, verifying it is refused.

That is enough to fail loudly if the framing, session mapping, stream routing or either allowlist breaks. No fixtures, no mocking framework.

The two authorization cases earn their place despite the ladder — a silent regression there is not a bug that shows up as a broken feature, it is one that shows up as an open door. Note what this check deliberately does not cover: hole punching. On loopback there is nothing to punch. NAT traversal is verified by M2 on real networks, by hand, and cannot be meaningfully unit-tested.

Packaging

The deliverable is one statically linked executable per platform, a few megabytes, with no runtime, no shared libraries and no config file. All roles are the same binary — the subcommand chooses — so there is exactly one artifact per platform.

v1 could treat non-Linux targets as an afterthought because only the relay was a real deployment. v2 has no relay, so every target is a first-class client and all three ship together.

Target triples

TargetForNotes
x86_64-unknown-linux-muslLinux boxes, home servers, a self-hosted relayFully static, so one file runs on Debian, Ubuntu, Alpine and an ancient CentOS alike.
aarch64-unknown-linux-muslARM boards, Raspberry Pi, ARM instancesSame build, different triple.
aarch64-apple-darwinApple Silicon MacsNative cargo build --release on the dev machine.
x86_64-apple-darwinIntel MacsCheap to add while the matrix is being written; drop it if nobody has one.
x86_64-pc-windows-msvcWindows clientsNo longer deferred. Requires a Windows CI runner — see below.

musl rather than gnu on Linux is still the right call: a glibc-linked binary inherits the build machine's glibc version and greets you with GLIBC_2.34 not found on an older box, while a musl binary has no such link to break. The cost is musl's slower allocator under heavy multi-threaded churn, which a byte pump never approaches.

Cross-compiling from a Mac no longer covers the matrix. cross handles the Linux targets, but x86_64-pc-windows-msvc needs the MSVC toolchain and Apple targets need Apple's SDK — neither is legitimately cross-buildable from the other's host. Three platforms means CI with three runners, not a clever local script. This is the concrete reason v2 skips rungs 0 and 1 of the old delivery ladder.

Delivery

v1's ladder started at scp and expected to stay there. That was correct for one relay and one client; it is wrong for three operating systems, because the bottom two rungs cannot even produce the artifacts.

The plan of record is cargo dist init. One command generates the GitHub Actions matrix across all three runners, checksums, a curl … | sh installer for macOS and Linux, a PowerShell irm … | iex installer for Windows, an MSI, and a Homebrew tap. Hand-writing three installers to arrive at the same place is strictly more work than running one command.

MechanismStatus
✓ cargo dist init, release on tag push The plan of record. Adopt at M6.
· cargo build --release and copy the binary by hand Fine for M1 through M5, while both ends are machines you are actively developing on.
✕ Hand-written MSI / WiX, pkg, apt repo, Docker image Not planned. cargo dist produces the ones that matter.
✕ Code signing and notarization Deferred. Gatekeeper and SmartScreen will warn on first run; document the right-click-Open dance. Lift when someone who is not you installs it.
Never bundle keys into the installer. It is tempting, now that setup needs an endpoint ID on each side, to bake them into a per-user build. Don't — the artifact is public, and a build that embeds an allowlist is a build that must be regenerated for every peer. The keys are generated on first run, on the machine that will hold them, and the IDs are exchanged afterwards.

Running it unattended

There is no VPS unit any more. Instead each machine runs its role under its own platform's service manager. This is the one place the pivot added work: v1 needed one systemd unit, v2 needs three mechanisms.

PlatformMechanismNotes
Linuxsystemd unitUnchanged in shape from v1, minus the capability line. StateDirectory=rtun holds the persisted key.
macOSlaunchd plist in ~/Library/LaunchAgentsA user agent, not a daemon — no root, and it stops when the user logs out, which is usually what you want on a laptop.
WindowsTask Scheduler, trigger At log onA bare exe cannot be a Windows service without a wrapper. Task Scheduler needs no wrapper and no admin rights. Reach for sc.exe plus a shim only if it must run before login.
 
# /etc/systemd/system/rtun.service — Linux
[Unit]
Description=rtun
After=network-online.target

[Service]
ExecStart=/usr/local/bin/rtun serve --tcp 22 --allow k51qzi5uqu5dl…
DynamicUser=yes
StateDirectory=rtun                # /var/lib/rtun holds the persisted key
Restart=always
RestartSec=2

[Install]
WantedBy=multi-user.target
No privileged ports anywhere, on any platform. v1 needed CAP_NET_BIND_SERVICE because the relay bound public low ports. v2's serving side only makes outbound loopback connections, and the connecting side binds whatever local port you pick — choose one above 1024 and the whole question disappears. There is no AmbientCapabilities line and no reason to run as root.
There is usually no firewall work at all. Both sides only ever send outbound UDP, which every consumer firewall already permits. If a corporate firewall blocks outbound UDP entirely, hole punching and the QUIC relay both fail together and the tunnel does not come up — see known ceilings.

Known ceilings

Deliberate simplifications, each with the condition that would justify lifting it. These are the items that will carry ponytail: comments in the source.

CeilingConsequenceLift it when
Both ends must run rtun No public ingress. You cannot hand a colleague an address, point a webhook at it, or open it in a browser. This is the price of the whole design. Never, within this scope. If you need public ingress, you need v1's relay — and you would run it alongside this, not instead of it.
Roughly one connection in ten cannot be hole-punched Symmetric NAT on both sides falls back to a relay, with that relay's latency and bandwidth. Never — it is a property of the networks, not the code. Report it honestly in rtun status so it is visible rather than mysterious.
Default discovery and relay are third-party infrastructure Connection setup depends on a service you do not run. Metadata — which keys talked, and when — is visible to it; payload is not, being end-to-end encrypted. You object to the dependency or the metadata. Then self-host iroh-relay; the $4 VPS from v1 does the job and now costs almost no bandwidth.
Outbound UDP is required A network permitting only TCP :443 blocks the tunnel entirely — direct and relayed alike. You actually hit such a network.
UDP payload capped at the QUIC datagram size, roughly 1200 bytes minus the 6-byte header Larger UDP datagrams are dropped, not fragmented. Harmless for DNS, WireGuard, game and voice traffic; breaks applications sending jumbo datagrams. A real workload needs it — then fragment across a dedicated stream per session.
One peer connection at a time No fan-out to several machines from one serve instance. A third machine needs in. This is a genuinely small change under iroh — the endpoint already accepts many connections — but the session tables need a peer dimension.
Flags instead of a config file Long command lines once there are many mappings and several allowed keys. The flag list outgrows a comfortable command line. Arrives sooner than in v1, since keys are long.
Key rotation is manual and mutual Losing a machine's state directory changes its identity; every peer's allowlist must be edited by hand. There is a fleet rather than a pair.
Binaries unsigned Gatekeeper and SmartScreen warn on first run. Someone who is not you installs it.

Prerequisite: the development machine has no Rust toolchain yet. Install with brew install rustup then rustup-init before starting M1. Confirm the current iroh release and its API at docs.rs/iroh before writing against the sketch in Transport — it reached 1.0 recently and the examples above are illustrative, not copied from a compiling build.

Explicitly out of scope

Named here so they do not get built by accident: public ingress for unmodified clients, HTTP-aware routing and subdomains, a web dashboard, metrics exporters, an enrolment or key-distribution server, more than two peers, mesh routing between peers, and any form of virtual network interface. Each is a larger project than the tunnel itself.

Worth separating from that list: a self-hosted relay is not out of scope, it is simply not needed on day one. It is a configuration change — point the endpoint at your own iroh-relay — rather than code to write.
