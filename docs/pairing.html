RustTunnel — Pairing Two Machines

Install rtun on both machines, let them learn each other's public key, and reach one machine's ports from the other. Fifteen minutes, no account, no server.

Draft v1 · 2026-08-08 · RustTunnel

Before you start

You need two machines you own and a shell on each. Nothing else — there is no signup, no config file and no central server to point at. The two machines find each other by public key through a public discovery service, and talk directly once they have.

The serving machine

The one with something on it you want to reach — a home box with SSH, a NAS, a database. It runs rtun serve and names which of its local ports may be reached.

The connecting machine

The laptop you are sitting at. It runs rtun connect and turns the far machine's ports into ports on its own 127.0.0.1.

Both directions

Each side must know the other's ID: the serving side to allow it in, the connecting side to dial it. That two-way exchange is the whole of pairing.

Step 1 — Install on both machines

PlatformCommand
macOS, Linux curl -fsSL https://raw.githubusercontent.com/lesslucifer/RustTunnel/main/packaging/install.sh | sh
Windows (PowerShell) irm https://raw.githubusercontent.com/lesslucifer/RustTunnel/main/packaging/install.ps1 | iex
From source cargo build --release, then copy target/release/rtun anywhere on your PATH.

The installer puts rtun in ~/.local/bin (%LOCALAPPDATA%\rtun\bin on Windows) and tells you if that directory is not on your PATH. If it says so, either add it to your shell profile or type the full path everywhere below — the walkthrough works the same either way.

Check it landed:

rtun --version
rtun --help

Step 2 — Read both IDs, and carry each to the other machine

On each machine:

rtun id
# 3ef09bf26bfd29946ee8e3da2d18d56bbd5cb8a40a817084b9343950b6bed842

That 64-character string is the machine's public key and its permanent address. It is generated the first time you run any rtun command, kept in ~/.local/state/rtun/secret.key, and stays the same across restarts and reboots. It is not a secret — it is safe to paste into chat, mail it to yourself, or read it aloud over the phone.

Write both down somewhere you can see them at once. The rest of this document calls them ID_HOME and ID_LAPTOP.

Only the key file is secret. secret.key is created owner-readable (0600) in an owner-only directory. Anyone who copies that file becomes that machine as far as the other side is concerned. Deleting it makes a new identity, which means re-pairing — the other side's --allow will no longer match.

Step 3 — On the serving machine, offer ports to that one peer

rtun serve --tcp 22 --allow ID_LAPTOP

Two allowlists are at work, and both matter:

FlagMeans
--allow IDOnly this peer may connect at all. Repeat it for more peers. It is required — there is no "allow anyone" mode.
--tcp PORTThis local TCP port may be reached through the tunnel. Repeat for more ports. A port you do not list is refused even to an allowed peer.
--udp PORTThe same, for UDP — a DNS resolver on 5353, a WireGuard endpoint on 51820.
--relay-onlySkip direct paths entirely. Slower; useful for testing and for networks where hole punching does not work.

Leave it running. It prints its own ID on the first line, then a line per event.

Nothing listening on 22 yet? --tcp 22 only means "port 22 may be reached" — it does not start SSH. On macOS, Remote Login is off by default and turning it on needs an administrator (System Settings → General → Sharing). To try the tunnel first without admin rights, offer a port you can serve yourself: run python3 -m http.server 8022 --bind 127.0.0.1 on the serving machine, use --tcp 8022 here and --tcp 2222:8022 in step 4, and fetch http://127.0.0.1:2222/ in step 5.

Step 4 — On the laptop, map the far port onto a local one

rtun connect ID_HOME --tcp 2222:22

2222:22 reads local-first: this machine's port 2222 becomes the far machine's port 22. Pick any free local port; it does not have to differ from the remote one, and on macOS anything below 1024 needs admin, so 2222 is the easy choice.

Within a few seconds both sides log the same connection from their own end:

INFO rtun::serve: admitted peer=51d710cbd4…
INFO rtun: established peer=51d710cbd4 path=relayed addr=relay:… rtt=104ms
INFO rtun: path selected peer=51d710cbd4 path=direct addr=ip:192.168.1.8:61393

path=relayed first and path=direct a moment later is the normal, healthy sequence — the two machines have to talk through the relay before they can talk directly. See the plan for why.

Step 5 — Use it

ssh -p 2222 127.0.0.1        # you are on the far machine
hostname                     # …and it says so

Any TCP client works the same way: point it at 127.0.0.1:2222 and it reaches port 22 on the other machine. For UDP, add --udp 5354:5353 on the connecting side and --udp 5353 on the serving side, then dig -p 5354 @127.0.0.1 example.com.

Leave both running. The connecting side reconnects on its own if the link drops — it retries with a growing delay and picks the peer back up when it returns, with no restart. The one thing it does not retry is a refusal: if the serving side's --allow does not list you, rtun connect says so and exits non-zero rather than hammering a permanent no.

Step 6 — Keep the serving machine serving, across reboots

PlatformSteps
macOS 
sed -e "s|__RTUN__|$HOME/.local/bin/rtun|" -e "s|__PEER__|ID_LAPTOP|" \
    -e "s|__PORT__|22|" -e "s|__STATE__|$HOME/.local/state/rtun|" \
    -e "s|__HOME__|$HOME|" packaging/com.rtun.serve.plist \
    > ~/Library/LaunchAgents/com.rtun.serve.plist
launchctl bootstrap gui/$UID ~/Library/LaunchAgents/com.rtun.serve.plist
launchctl list com.rtun.serve      # a PID means it is up
Logs land in ~/Library/Logs/rtun-serve.log. To remove it: launchctl bootout gui/$UID/com.rtun.serve and delete the plist.
Linux 
sudo cp packaging/rtun.service /etc/systemd/system/
sudoedit /etc/systemd/system/rtun.service   # set --allow and the ports
sudo systemctl enable --now rtun
systemctl status rtun
The unit uses StateDirectory=rtun, so the identity lives in /var/lib/rtun and survives restarts. Note that this is a different identity from the one your user account got — run sudo systemctl start rtun once and read the ID out of journalctl -u rtun before allowlisting it.
Windows 
schtasks /create /tn rtun /sc onstart /ru SYSTEM ^
  /tr "%LOCALAPPDATA%\rtun\bin\rtun.exe serve --tcp 22 --allow ID_LAPTOP"
Same caveat as systemd: running as SYSTEM gives it a different state directory, so read its ID from its own first run.

When it does not work

What you seeWhat it means
Error: closed by peer: not in --allow (code 1), exit 1 The serving side does not list this machine's ID. Re-read rtun id on the connecting machine and check it against the --allow on the serving one — a truncated paste is the usual cause.
Serving side logs refused: port not in --tcp The mapping names a remote port the serving side never offered. Add --tcp <that port> there and restart it.
Client hangs, connecting side logs retrying … retry_in= The far machine is not reachable — not running, asleep, or offline. This is the retry loop doing its job; it recovers by itself when the peer returns.
binding tcp 127.0.0.1:2222: Address already in use Something else holds that local port, often an rtun connect you started earlier. Pick another local port or stop the old one.
Stays path=relayed Working, but going the long way round. Both networks are behind NATs that could not be punched through. Everything still functions, with more latency and less bandwidth.
Both machines print the same ID They are sharing a state directory — you are running both roles on one machine. Give one of them its own: RTUN_STATE_DIR=/tmp/rtun-b rtun connect ….
