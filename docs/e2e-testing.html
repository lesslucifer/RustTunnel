RustTunnel — End-to-End Test Plan

How to exercise every phase of the tunnel on one MacBook — the rig, the per-task procedure, the substitutions each one makes, and the four checks that a single machine can never honestly produce.

Draft v1 · 2026-08-08 · RustTunnel

Verdict

Yes — 20 of the 23 WBS tasks can run on this Mac, most at full fidelity. What one machine cannot produce is any claim about two machines: cross-machine dialing, hole punching between real NATs, and installing on Linux or Windows. Everything the user actually asked for — connection, round trip, flow — is fully reachable here.

Full fidelity locally

Both allowlists, both data planes, framing, concurrency, bulk transfer, session reaping, the datagram cap, reconnect with backoff, and the 24-hour soak. 12 tasks. These lose nothing by running on one host.

Degraded but worth running

Path reporting, dial-by-ID, SSH end to end, WireGuard, network-change recovery, clean install, service restart, pairing. 8 tasks. Each proves the mechanism but not the topology; the exact loss is named per task.

Cannot run here at all

0.2 three-platform CI, 2.2 cross-NAT direct, 6.1 release artifacts. Three tasks — two want a git remote, one wants a second network.

A local run never retires 2.2. The single most important thing this document does is keep that distinction intact. On one Mac the path upgrades to direct because iroh discovers the host's own LAN address — there is no NAT between the two processes, so nothing was punched. Every check below can pass while the premise of v2 remains unproven. File local evidence under evidence/local/, never under evidence/<task-id>/.

Hình 1 — Both roles on one host. The dotted path is the same rig with --relay-only on both sides, which is the only way to get real RTT and real packet loss into a local run.

Prelude

cd ~/Documents/proj/misc/RustTunnel
export PATH=$HOME/.cargo/bin:$PATH        # cargo is not on the default non-login PATH
cargo build --release
R=$PWD/target/release/rtun

A=/tmp/rtun-a B=/tmp/rtun-b C=/tmp/rtun-c   # three "machines": serve, connect, stranger
mkdir -p $A $B $C
IDA=$(RTUN_STATE_DIR=$A $R id)
IDB=$(RTUN_STATE_DIR=$B $R id)
IDC=$(RTUN_STATE_DIR=$C $R id)
[ "$IDA" != "$IDB" ] || { echo "same identity — RTUN_STATE_DIR is not taking effect"; exit 1; }

# the "remote service", unprivileged, carrying a token only it can serve
mkdir -p /tmp/rtun-www && uuidgen > /tmp/rtun-www/token
(cd /tmp/rtun-www && python3 -m http.server 8022 --bind 127.0.0.1) &

Role A is the home box, role B is the laptop, role C exists only to be refused. Every run captures both sides: 

RTUN_STATE_DIR=$A $R serve   --tcp 8022 --allow $IDB          > serve.log   2>&1 &
RTUN_STATE_DIR=$B $R connect $IDA --tcp 2222:8022             > connect.log 2>&1 &
Why python3 -m http.server and not sshd as the default service. It needs no admin rights, it is threaded since Python 3.7 so it can serve the concurrency check, and the token file gives the test a value that only the far service can produce. sshd stays in the plan for 3.1, but it requires enabling Remote Login and its usual proof — hostname differing — is exactly the proof one machine cannot give.

The WBS text for 2.1 is wrong about timing, and the check should be fixed rather than the code. It says a same-machine run "reports direct immediately, with no relay in between". It does not — establishment is relayed through the public n0 relay and the direct path is selected about 250 ms later, exactly as Hình 3 of the plan describes. Assert reaches path=direct within a few seconds; asserting immediacy makes a correct implementation look broken.

One product finding: connect exits 0 when the allowlist refuses it. The refusal is logged on both sides and the close code is correct, but the process returns success, so a script can only tell refusal from a clean shutdown by grepping the log. This matters more than it looks once 5.1 lands reconnect: a refused peer must not be retried forever, an absent peer must be. Distinguish ApplicationClosed from the other close reasons and exit non-zero on it.

Hình 3 — Proving the byte path on one host. The token establishes which service answered; killing connect and losing the port establishes that rtun, not the kernel, was carrying it.

3.1 · One connection end to end degraded

curl -s http://127.0.0.1:2222/token          # must equal /tmp/rtun-www/token
diff <(curl -s http://127.0.0.1:2222/token) /tmp/rtun-www/token && echo TOKEN-OK
grep 'port=8022' serve.log                   # serve side names the target port
kill %2 ; curl -sv http://127.0.0.1:2222/token   # expect: Connection refused

Then the SSH variant, which is the target's literal wording. Enable Remote Login first (System Settings → General → Sharing, or sudo systemsetup -setremotelogin on), serve --tcp 22, map 2222:22, and run ssh -p 2222 127.0.0.1 'hostname; uptime'.

What 3.1 loses on one Mac. Its evidence requirement is "the local hostname before connecting and the remote hostname inside the session" — and here they are the same string. The token check above replaces that proof and is strictly stronger about the byte path, but it says nothing about reaching another host. The SSH run still earns its place: it exercises an interactive, latency-sensitive, bidirectional stream that curl does not.

3.2 · Port allowlist local

RTUN_STATE_DIR=$B $R connect $IDA --tcp 3333:9999 > connect-deny.log 2>&1 &
curl -sv http://127.0.0.1:3333/            # must fail
grep -i 'refus' serve.log                  # serve side names port 9999

Full fidelity — the refusal is a comparison against --tcp, indifferent to topology.

3.3 · Concurrency and clean close local

# two distinct payloads that must not interleave, plus one bulk transfer
dd if=/dev/urandom of=/tmp/rtun-www/red   bs=1m count=50
dd if=/dev/urandom of=/tmp/rtun-www/blue  bs=1m count=50
dd if=/dev/urandom of=/tmp/rtun-www/big   bs=1m count=100
shasum -a 256 /tmp/rtun-www/{red,blue,big} > /tmp/expected.sha

curl -s http://127.0.0.1:2222/red  -o /tmp/got-red  &
curl -s http://127.0.0.1:2222/blue -o /tmp/got-blue &
wait
curl -s http://127.0.0.1:2222/big  -o /tmp/got-big

shasum -a 256 /tmp/got-{red,blue,big}      # compare against /tmp/expected.sha

Three checks in one run: the two concurrent fetches prove stream independence and that payloads do not cross, and all three matching digests prove byte-exactness plus clean close — a truncated or unterminated stream cannot produce a matching digest.

3.4 · Repeat relayed local

# both roles with --relay-only, then rerun 3.1 and 3.3 against a 10 MB file
This is the run that matters most on one machine, and the one to shrink. Loopback has no loss, no reordering and sub-millisecond RTT, so flow-control and framing bugs hide in the direct run and surface in the relayed one — measured RTT through n0 was 250–350 ms. Drop the bulk file to 10 MB for this pass: the n0 relay is a free shared service and 100 MB each way is not a reasonable thing to push through it.

P4 — UDP forwarding

4.1 · DNS round trip local

brew install dnsmasq
dnsmasq -d -p 5353 --listen-address=127.0.0.1 --bind-interfaces -S 1.1.1.1 &   # no sudo: port > 1024

RTUN_STATE_DIR=$A $R serve   --udp 5353 --allow $IDB      > serve.log   2>&1 &
RTUN_STATE_DIR=$B $R connect $IDA --udp 5354:5353         > connect.log 2>&1 &
dig -p 5354 @127.0.0.1 example.com

A real resolver answering a real query, all unprivileged. Pass condition is a populated ANSWER section, which also proves the reply found its way back to dig's ephemeral source port — the session-table round trip, not just the outbound leg.

4.2 · WireGuard handshake degraded

Two utun interfaces on one host, each peering with the other through the tunnel, is possible and not worth it: the two interfaces compete for routes to the same address space and a failure is as likely to be macOS routing as rtun. What 4.2 uniquely proves beyond 4.1 is sustained bidirectional datagram flow from a fixed source port at close to the size cap. Substitute that directly: 

# serve side: a UDP echo at 1000-byte datagrams
python3 -c 'import socket;s=socket.socket(2,2);s.bind(("127.0.0.1",5353))
while 1:
    d,a=s.recvfrom(2048);s.sendto(d,a)' &

# connect side: 60 s of traffic from ONE fixed source port, count losses
python3 -c 'import socket,time
s=socket.socket(2,2);s.bind(("127.0.0.1",40001));s.settimeout(2);n=lost=0
end=time.time()+60
while time.time()<end:
    p=b"x"*1000;s.sendto(p,("127.0.0.1",5354));n+=1
    try: s.recv(2048)
    except socket.timeout: lost+=1
    time.sleep(0.05)
print(n,"sent",lost,"lost")'

Pass: loss stays near zero and the session survives the full minute without the table churning. 4.2 itself stays open — file this as evidence/local/4.2-substitute/, and if a real WireGuard check is wanted before a second machine exists, two Linux containers with NET_ADMIN are far easier than two utuns (Docker is installed here but its daemon is not running).

4.3 · Session reaping local

for p in 40001 40002 40003 40004 40005; do
  python3 -c "import socket,sys;s=socket.socket(2,2);s.bind(('127.0.0.1',int(sys.argv[1])))
s.sendto(b'hi',('127.0.0.1',5354))" $p
done
grep sessions= serve.log | tail -1        # expect 5
lsof -p $(pgrep -f 'rtun serve') -i UDP | wc -l   # independent confirmation
sleep 75                                   # past the 60 s idle timer
grep sessions= serve.log | tail -1        # expect 0
lsof -p $(pgrep -f 'rtun serve') -i UDP | wc -l   # back to the baseline

Five distinct source ports must produce five distinct sessions — a single session would mean the key is wrong. lsof is the honest cross-check: it counts sockets the kernel actually holds, independently of what rtun believes.

4.4 · Oversize datagram local

python3 -c 'import socket;socket.socket(2,2).sendto(b"x"*2000,("127.0.0.1",5354))'
grep -iE 'drop|oversiz|too large' connect.log
This check is better on one Mac than across a network. The loopback MTU is 16384, so the 2000-byte datagram is accepted by the kernel without complaint. Any drop therefore comes from rtun's own cap check — which is precisely the known ceiling the task exists to make fail loudly. Across a real network the same test could pass for the wrong reason: path MTU, not the cap.

P5 — Resilience

5.1 · Reconnect with backoff local

kill $(pgrep -f 'rtun serve')
sleep 180                                       # watch connect.log retry
grep -E 'retry|reconnect|backoff' connect.log   # gaps must grow: 1s 2s 4s 8s …
RTUN_STATE_DIR=$A $R serve --tcp 8022 --allow $IDB >> serve.log 2>&1 &
sleep 10 && curl -s http://127.0.0.1:2222/token  # fresh session through the recovered link

Full fidelity. Backoff is a timer inside one process and the far side's absence is absence either way.

5.3 · 24-hour soak local

caffeinate -s &                                  # sleep would pause both roles and void the run

Fake-green traps

Five ways a local run passes while the tunnel is broken. Each is cheap to defend against.

One identity wearing two hats

Forget RTUN_STATE_DIR on either role and both are the same key — the allowlist trivially matches itself. The prelude's IDA != IDB assertion is not decoration; keep it at the top of every script.

A port both sides can reach

Both roles share one loopback, so a serve side that connected to the connect side's socket would still answer. Never reuse a port number across roles, and keep the local mapped port (2222) different from the remote one (8022).

Loopback is a perfect network

No loss, no reordering, no RTT. Flow control, window handling and stream framing are barely exercised. Every data-plane check gets a --relay-only repeat, which is where those bugs actually appear.

path=direct that punched nothing

The most tempting misread in the whole plan. A local direct line proves the reporting code works. It is not evidence for 2.2 and must never be filed as such.

pkill -f rtun hits both roles

Not hypothetical — it broke the first 2.3 run here. Tearing down one test's serve by pattern killed a long-running relay hold in another shell, which then logged closed: timed out and looked exactly like a product failure. On a one-Mac rig, kill by PID. Never by pattern.

The service answering directly

curl 127.0.0.1:8022 works with rtun dead. Always test the mapped port, and always confirm it stops answering once connect is killed — that negative is half the proof.

One thing to add before P4

Every check above reads existing log lines except 4.3, which needs a session count that nothing currently exposes. The plan floats a rtun status subcommand; the test does not need it.

Log sessions=N when the UDP table changes. One line on create and one on reap makes 4.3 a grep, cross-checked by lsof -i UDP on the serve pid. rtun status is a nicer product feature and a worse test hook — it needs a control channel, and a log line needs nothing. Add the subcommand when a human wants to ask, not because a test does.
