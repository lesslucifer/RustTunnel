RustTunnel — Work Breakdown Structure

Every task carries a target, an end-to-end check, and a filed piece of evidence. Nothing is done until all three exist.

Draft v1 · 2026-08-08 · RustTunnel

How to read this

The design lives in the implementation plan. This document is the execution track: what gets built, in what order, and — the part that matters — how each piece is proven to work against a real network rather than against an assumption. The e2e test plan is the operational half: the commands for each check below, which of them run on one machine, and what each single-machine substitute costs.

Target

One sentence describing the observable state that makes the task done. Not "implement X" — a condition you can stand in front of and check.

E2E check

Exercised through the real binary, over a real network, using a real client. No unit tests here, no mocks, no in-process shortcuts.

Evidence

A file committed under evidence/<task-id>/. If it was not captured, the task is not done — memory of a passing test is not evidence. Single-machine substitutes go on their own shelf at evidence/local/<task-id>/.

What "end-to-end" means here. A real ssh, dig or wg talking to a real service on the far machine, through two rtun processes, over a network path neither process controls. The five in-process cases in the plan's one check are a fast regression net that runs in CI — they are necessary and they are not sufficient. Loopback cannot prove NAT traversal, because there is nothing to traverse. Two rtun processes on one machine sit between those poles: real binaries and a real QUIC connection, but one kernel and no NAT. The coverage matrix rules on each task — 12 of 23 lose nothing that way, 8 are worth running as substitutes, 3 cannot be attempted at all.

Evidence convention

KindFiled asMust contain
Terminal transcriptevidence/<id>/session.txtThe full command line and its output, unedited. Redact keys only if genuinely secret — endpoint IDs are public and should stay readable.
Process logevidence/<id>/serve.log, connect.logBoth sides, with timestamps. A one-sided log proves half a story.
Network contextfirst lines of session.txtWhich two networks, and how they differ. "Both on my Wi-Fi" invalidates most of Phase 2.
Screenshotevidence/<id>/*.pngOnly where text cannot carry it — a CI run page, a Windows service dialog.
Single-machine substituteevidence/local/<id>/Same contents, plus a first line naming the substitution and what the target still wants. Never filed as a cross-machine task's evidence — see the filing rules.

P0 — Foundation

DeliverableTargetE2E checkEvidence
0.1 Repo skeleton and toolchain A release build succeeds on the dev Mac and the CLI exposes serve, connect and id. Run the built binary's --help and each subcommand's --help. 0.1/session.txt — build tail plus all four help outputs.
0.2 Three-platform build check in CI cargo build and cargo test pass on Linux, macOS and Windows runners. Push a branch; all three jobs go green without a local machine involved. 0.2/ci-run.png plus the run URL in session.txt.
Why the Windows runner exists this early. It costs an hour now and catches a platform-specific break the day it lands. Discovering at P6 that a core dependency does not build on Windows means unwinding weeks of decisions. This is the cheapest insurance in the plan.

P1 — Identity

DeliverableTargetE2E checkEvidence
1.1 Persistent identity and rtun id The endpoint ID is stable across restarts; the key file is owner-readable only. Print the ID, restart, print again — identical. Delete the state directory, print again — different. Check file permissions. 1.1/session.txt showing all three IDs and the permission bits.
1.2 Dial by endpoint ID connect establishes a connection to serve given only its ID, from a different machine. Two machines, two terminals. Each side logs the other's ID; the IDs match what rtun id printed. 1.2/serve.log and connect.log from both machines.
1.3 Peer allowlist A peer whose key is not in --allow is refused; a listed peer is admitted. Connect with an unlisted key — refused, with a message naming the rejected key. Add it, retry — admitted. 1.3/session.txt with both attempts, and the serve-side log line for the rejection.

P2 — Direct path risk gate

This phase decides whether the project as designed is possible on the networks you actually have. It is three tasks and half a day, and it comes before any forwarding code exists.

DeliverableTargetE2E checkEvidence
2.1 Path reporting Both sides log path=direct or path=relayed on establishment, and log again when the path upgrades. Run both roles on one machine — establishment is relayed, then direct is selected within a few seconds at the host's own LAN address. 2.1/session.txt.
2.2 Cross-NAT direct connection path=direct between two machines on two genuinely different networks. Home box on the home ISP, laptop tethered to a phone on cellular. Both sides must independently report direct. 2.2/serve.log, connect.log, and a first line in session.txt naming both networks and both carriers.
2.3 Relay fallback works With direct paths disabled, the connection still establishes and stays up. Force relay mode, connect, hold the link for five minutes, confirm it does not drop. 2.3/connect.log showing path=relayed at both ends of the window.
2.1's check was corrected after running it. It previously read "reports direct immediately, with no relay in between", which no correct implementation can satisfy: establishment goes through the relay so the two sides can talk before they can talk directly, and the punch upgrades the path underneath — Hình 3 of the plan says so explicitly. Measured on one machine, direct arrives 120–320 ms after relayed. Asserting immediacy makes working code look broken.
Gate condition. If 2.2 reports relayed between your two real networks, hole punching is not available to you and the entire premise of v2 is unavailable — stop and reconsider before building a data plane on it. Try a third network first, because one symmetric NAT is survivable and two are not; if it still fails, the honest options are to keep v1's relay design or to accept relayed operation and lose the latency and bandwidth argument that motivated the pivot. Do not proceed to P3 on a relayed-only result and hope.

P3 — TCP forwarding

DeliverableTargetE2E checkEvidence
3.1 One connection end to end An interactive SSH session runs through the tunnel to the far machine. ssh -p 2222 127.0.0.1 on the laptop reaches the home box. Run hostname and uptime inside the session to prove it is the remote host, not the local one. 3.1/session.txt showing the local hostname before connecting and the remote hostname inside the session.
3.2 Port allowlist on the serving side A stream naming a port that serve did not offer is refused. Map a local port to a remote port absent from serve --tcp; the connection is refused and the reason is logged. 3.2/session.txt plus the serve-side rejection line.
3.3 Concurrency and clean close Simultaneous connections stay independent, and closes propagate in both directions. Two concurrent sessions carrying distinct payloads that must not interleave, plus a 100 MB file transferred and checksummed at both ends. 3.3/session.txt with matching sha256 on both sides and both session transcripts.
3.4 Re-verify on the relayed path Everything in 3.1 and 3.3 also works with direct paths disabled. Force relay mode and repeat the two checks. 3.4/session.txt.

P4 — UDP forwarding

DeliverableTargetE2E checkEvidence
4.1 DNS round trip A real resolver on the far side answers a real query through the tunnel. dig against the local forwarded port returns a populated ANSWER section for a known name. 4.1/session.txt with the full dig output.
4.2 WireGuard handshake A WireGuard peer completes a handshake and passes traffic through the tunnel. wg show reports a recent handshake, and a ping crosses the WireGuard interface. 4.2/session.txt with wg show and ping statistics.
4.3 Session reaping Idle UDP sessions and their sockets are released; the table returns to empty. Open several sessions from distinct source ports, stop sending, wait past the idle timeout, and read the session count back. 4.3/session.txt showing the count before, during and after the timeout.
4.4 Oversize datagram behaviour A datagram larger than the cap is dropped predictably and visibly, not silently corrupted. Send a 2 KB datagram; confirm it does not arrive and that the drop is logged with the reason. 4.4/session.txt plus the log line.
4.4 tests a known ceiling, not a bug. The datagram size cap is a deliberate simplification. The check exists so the limit fails loudly and legibly at the boundary, rather than presenting as an application that mysteriously misbehaves under load.

P5 — Resilience

DeliverableTargetE2E checkEvidence
5.1 Reconnect with backoff The connecting side retries with growing delay and recovers by itself when the far side returns. Kill serve, watch the retries, restart it after a few minutes, then open a fresh SSH session successfully. Separately, point connect at a peer that refuses it — it must give up, not retry. 5.1/connect.log — timestamps must show the backoff growing, then a successful reconnect, plus the refusal case exiting non-zero.
5.2 Survives a network change The tunnel recovers unattended across laptop sleep and a Wi-Fi to cellular switch. Sleep the laptop five minutes and wake it. Separately, switch it from Wi-Fi to tethering mid-session. No manual restart in either case. 5.2/connect.log covering both transitions, and the post-recovery path type.
5.3 24-hour soak Both processes survive a day of light periodic traffic with no memory growth and no death. Run a small transfer every few minutes for 24 hours; sample resident memory hourly. 5.3/soak.txt — hourly memory samples and final uptime for both processes.
Reconnect must distinguish "refused" from "gone". Running 1.3 surfaced that connect exits 0 when the allowlist turns it away — correct close code, correct log line, wrong exit status. Today nothing depends on it; the moment 5.1 adds a retry loop it becomes a bug that retries a permanent refusal forever. Treat ApplicationClosed as terminal and exit non-zero, and retry everything else.
5.2 is where laptops actually break. Sleep and network switches are the normal operating conditions of the machine this runs on, not edge cases. A tunnel that needs a manual restart after every lid close is a tunnel nobody keeps using — which makes this the phase that decides whether the tool survives contact with daily use.

P6 — Ship

DeliverableTargetE2E checkEvidence
6.1 Release artifacts A tag push produces binaries for all target platforms, with checksums. Push a tag; the release appears with every expected artifact attached. 6.1/release.png plus the release URL and the artifact list.
6.2 Install on a clean machine The published installer works on a machine that has never held the source or a toolchain. On a fresh VM or a fresh user account per OS: run the installer, then rtun id. 6.2/<os>-session.txt for each platform, starting from the install command.
6.3 Runs as a service, survives reboot The tunnel comes back after a reboot with no human action, on each platform. Install the service, reboot, and confirm from the far side that the tunnel is up before anyone touches the machine. 6.3/<os>-session.txt — the far side's log showing reconnection, timestamped after the reboot.
6.4 Pairing walkthrough A person following written steps can pair two machines without reading the source. Hand the steps to someone else, or to yourself on an unfamiliar machine, and follow them literally. 6.4/session.txt plus a note of every step that needed improvisation.
6.4 is the only task with a human in the loop, and it is not optional. The pairing flow requires reading an ID off one machine and passing it to another, in both directions. That is exactly the kind of step that is obvious to whoever designed it and confusing to everyone else. Every improvisation the check records is a documentation bug.

Definition of done

A task is done when all four hold. Three out of four is an in-progress task, regardless of how finished the code feels.

Condition
1The target is observably true, checked by the person claiming it.
2The E2E check ran against real binaries over a real network, with no mocks or in-process shortcuts.
3Evidence is committed under evidence/<task-id>/, unedited, showing both sides where two sides exist.
4The in-process regression check still passes, so the new work did not break the old.
Evidence is a gate, not paperwork. The whole design rests on claims about NAT behaviour, sleep recovery and cross-platform installs — none of which can be confirmed by reading the code, and all of which will be re-litigated in three months when something breaks. A captured log answers "did this ever actually work" in seconds. A memory of it does not.
