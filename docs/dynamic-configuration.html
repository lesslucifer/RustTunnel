Dynamic configuration and the admin UI

Add and remove named peers and ports on a running tunnel, from a local web panel, without a restart and without dropping the connection.

Draft v1 · 2026-08-22 · RustTunnel

What changed and why

Both of rtun's allowlists used to be command-line arguments read once at startup. That made every change a restart: editing --allow or --tcp meant killing the process, which dropped every live connection and every UDP session on it. For a tool whose whole job is holding a long-lived link, "restart to add a port" is the wrong shape.

The allowlists are now backed by a configuration file that both roles read live, and a small authenticated web panel edits it. The tunnel keeps running while it changes.

The promise. A port offered at 10:00 is reachable at 10:00. A peer removed at 10:05 loses its open connection at 10:05 — not whenever it next reconnects.

The model

One file, config.toml in the state directory, holds both roles' settings. A change is applied by one writer path and observed by many cheap readers.

Hình 1 — One writer, many readers. Nothing is published until it has both validated and reached disk.

Readers hold an immutable Arc<Config> snapshot, so the per-stream and per-datagram allowlist checks stay free and never block a writer. The order in validate → write → publish is deliberate: what is running is always what is on disk, and a rejected or unwritable edit changes neither.

Who may reach what

Grants are per peer, with a shared set for the common case. A peer reaches serve.shared plus its own offers, and only while both the peer entry and the port entry are enabled.

EntryMeaning
serve.sharedOffered to every enabled peer.
serve.peers[].offersOffered to that one peer. Not reachable by any other peer.
enabled = falseParked: the row and its name are kept, the grant is not in force.
connect.bindingsLocal listeners on the connecting side, local → remote.

Parking matters more than it looks. Deleting a peer throws away a 64-character key you would have to paste again; disabling it keeps the name and the history while removing the access. The UI offers both, and the enforcement path treats a parked entry exactly like an absent one.

A parked entry is not a soft grant. Config::admits returns false for a disabled peer, and granted() returns None rather than an empty list — the caller cannot mistake "parked" for "allowed, but no ports".

Enforcement while running

Reading the config live is only half of it. The other half is that a change must reach connections that already exist.

sequenceDiagram
  participant U as Admin UI
  participant S as serve
  participant P as Peer (connected)
  P->>S: QUIC connection (admitted)
  U->>S: DELETE /api/peers
  Note over S: watch channel fires
  S->>P: close(code 1, "access revoked")
  Note over P: connect exits — a refusal is permanent,
so it does not retry-loop
Hình 2 — Revocation reaches a connection that is already open.
  • TCP — the port allowlist is checked per stream, so a withdrawn port refuses the next stream on an existing connection.
  • UDP — checked per datagram, and a config change also closes sessions whose port lost its grant, because a UDP session holds an open socket to the local service.
  • Peers — a watcher per connection closes it the moment the peer stops being admitted, whether it was removed or merely disabled.
  • Bindings — the connecting side reconciles its listener set: new rows bind, removed rows drop (releasing the port), and a changed remote port re-points the pump without rebinding.

A binding whose port is already in use is reported on its own row with the OS error and retried on the next change. It does not fail the process, and it does not disturb the listeners that did bind.

Security of the admin surface

The admin port can grant a peer access to loopback services, so it is treated as a credential-bearing surface rather than a convenience.

Loopback by default

--admin 7000 binds 127.0.0.1. Exposing the panel requires naming an interface (--admin 0.0.0.0:7000) and logs a warning when you do.

Token, compared in constant time

128 bits of CSPRNG output in admin.token, created 0600. Persisted rather than regenerated so an open tab survives a restart.

Header-only mutations

Reads accept the token in the URL so the printed link works. Writes require an Authorization header, which a cross-origin form cannot set.

The URL does not linger

The page moves the token into sessionStorage and strips it from the address bar on load, so it stops leaking through history and bookmarks.

The token is as sensitive as the allowlist it edits. Anyone who holds it can grant a peer access to your loopback services.

Backward compatibility

Every documented invocation still works. Flags seed the config on first run: they add what is missing and never overwrite or re-enable an entry that has been edited, so re-running the same command is idempotent rather than additive.

rtun serve --tcp 22 --allow $ID behaves exactly as before. The one deliberate relaxation is that --allow is no longer unconditionally required: with --admin, a cold start with no peers is valid, because adding the first peer is precisely what the panel is for. Without either, the command still fails rather than starting a server nothing can reach.

Verification

The dynamic behaviour is covered by tests that run both roles in-process on loopback and change the configuration mid-flight — the only way to check a promise about a running tunnel.

mutation_applies_with_no_subscriberA real bug found this way — see below.

These were checked against deliberate sabotage: disabling the eviction watcher and neutering listener reconciliation failed exactly the five tests that cover those behaviours, and left the rest green. A test that cannot fail is not evidence.

Bug caught during development. tokio::watch::Sender::send returns an error and discards the value when there are no subscribers. The first implementation used let _ = tx.send(...), so any edit made before the data plane subscribed was silently dropped — including every edit in a process whose config is only ever touched through the UI. It is send_replace now, and mutation_applies_with_no_subscriber pins the behaviour.

Beyond the suite, the feature was exercised end to end with two real processes: both started with empty configs, were configured entirely over the HTTP API, upgraded to a direct path, carried real HTTP traffic through a port bound at runtime, then had that port withdrawn and the peer revoked — each taking effect immediately.

The panel

One embedded HTML file, no build step and no framework, so cargo build remains the only build and the binary stays the only artifact. It shows the panel matching the running role, polls every four seconds (and not while the tab is hidden) to keep the live path and bind status honest, and reports validation errors from the server verbatim rather than guessing.

Motion follows the project's usual restraint: short ease-out transitions, press feedback on buttons, a one-time stagger on first paint, nothing entering from scale(0), and prefers-reduced-motion dropping movement while keeping opacity.
